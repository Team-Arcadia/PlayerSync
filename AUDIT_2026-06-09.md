# Audit PlayerSync — 9 juin 2026

**Cible** : Team-Arcadia/PlayerSync, NeoForge 1.21.1, v2.1.5 (16 fichiers Java, ~7 500 lignes)
**Objectifs** : optimisation serveur, audit sécurité, correction des failles de duplication.
**Méthode** : revue complète du code source (VanillaSync, JDBCsetUp, ModsSupport, ModCompatSync, CommandInit, services util) en croisant les chemins save/restore/join/logout/death.

Le code porte déjà de nombreux correctifs (guards `last_server`, 2-phase commit, locks par joueur, HikariCP, snapshots différés). L'audit s'est donc concentré sur les failles **résiduelles**. 9 corrections ont été appliquées directement dans le code (marquées `AUDIT-1` à `AUDIT-9`).

---

## 1. Corrections appliquées

### 🔴 AUDIT-1 — Sécurité : NBT-bomb / DoS (`VanillaSync.deserializeBinaryBase64Tag`)
`NbtIo.readCompressed(..., NbtAccounter.unlimitedHeap())` décompressait sans limite tout blob `BNBT:` venant de la base. Quelques Ko de gzip malveillant ou corrompu pouvaient gonfler en gigaoctets → OOM et crash du serveur au moment du restore. La garde `max_inventory_size_bytes` ne protégeait que la taille *compressée* à l'écriture.
**Fix** : `NbtAccounter.create(2 × max_inventory_size_bytes)` (20 Mo par défaut).

### 🔴 AUDIT-2 — Duplication : entité périmée dans la file d'auto-save (`onServerTick`)
`autoSaveQueue` garde une **référence forte** vers l'entité `ServerPlayer` capturée au remplissage. Scénario : le joueur est en file → il droppe ses items → se déconnecte (le logout-save commit) → se reconnecte sur le même serveur → la file traite l'ancienne entité, dont l'inventaire reflète l'état **pré-logout**. Les gardes existantes (online=0, last_server) ne bloquaient pas ce cas car le joueur était re-online sur le même serveur → écrasement de l'état frais par l'ancien = **duplication des items droppés**.
**Fix** : avant tout snapshot, vérification que l'instance est encore l'entité vivante (`getPlayerList().getPlayer(uuid) == player` + `!hasDisconnected()`).

### 🟠 AUDIT-3 — Duplication : `join_peer_alive_max_wait_seconds` ignoré (`doPlayerJoin`)
L'option (défaut 600 s, documentée « SAFE — never force-claim on an alive peer ») n'était **jamais lue** : le code force-claimait après 2 s codées en dur, exactement le scénario de dup décrit dans le commentaire de la config (le claim vole la propriété pendant qu'une save du pair est encore en vol → l'état du pair est perdu et peut dupliquer avec des ItemEntity déjà spawnés).
**Fix** : la config est honorée quand `kick_when_already_online=false` ; le grace de 2 s est conservé quand le kick est actif (un row online=1 sans flag qui a survécu au kick-check est quasi certainement une ghost session — évite de verrouiller le joueur dehors).

### 🟠 AUDIT-4 — Config morte : pool Hikari (`JDBCsetUp.initPool`)
`hikari_pool_max_size` et `hikari_leak_threshold_ms` existaient dans la config mais le pool était codé en dur (15 / 25 000 ms). Les admins ne pouvaient pas dimensionner le pool selon leur hardware.
**Fix** : les deux valeurs sont lues depuis la config (fallback sur les anciennes valeurs).

### 🟠 AUDIT-5 — Perf : `SELECT *` au join (`doPlayerJoin`)
La lecture principale du join rapatriait **toutes** les colonnes, dont le MEDIUMBLOB `advancements` (jusqu'à plusieurs Mo de JSON pour un joueur vétéran), jamais utilisé dans ce chemin (les advancements sont gérés par `onDataPackSyncEvent`).
**Fix** : liste de colonnes explicite. Réduit fortement le transfert réseau et la pression sur le buffer pool MySQL à chaque connexion.

### 🔴 AUDIT-6 — Perf : SQL + I/O disque sur le main thread (`onDataPackSyncEvent`)
À chaque join, le handler exécutait sur le **thread principal** : un SELECT MySQL bloquant (5–200 ms selon la latence réseau), une écriture du fichier advancements, puis `PlayerAdvancements.reload()`. C'était le dernier gros point de blocage main-thread restant.
**Fix** : SELECT + écriture fichier déportés sur l'executor ; seul `reload()` (état serveur vivant) revient sur le main thread via `server.execute()`, avec re-vérification que le joueur est toujours en ligne.

### 🟠 AUDIT-7 — Perf : mécanismes périodiques en triple exemplaire
Trois systèmes de sauvegarde périodique se superposaient : refill tick toutes les 5 min (codé en dur), `PeriodicSaveService` toutes les 10 min (configurable), et l'event vanilla `SaveToFile` (~5 min). De même, le heartbeat `server_info` était écrit par trois chemins : le tick handler (30 s), `HeartbeatService` (30 s), et un piggyback **par joueur et par sauvegarde** (35 joueurs = 35 UPDATE identiques par cycle d'autosave).
**Fix** : suppression du refill tick et du heartbeat tick (le drain 1 joueur/tick est conservé, alimenté uniquement par `PeriodicSaveService`) ; piggyback rate-limité à 1 toutes les 15 s. Réduit la charge SQL périodique d'environ deux tiers.

### 🟡 AUDIT-8 — Sécurité : helpers SQL à injection supprimés (`JDBCsetUp`)
`executeQuery(String.format)` et `update(String, String...)` interpolaient des valeurs directement dans la chaîne SQL. Zéro appelant dans le code — mais une surface d'injection prête à servir au prochain développeur pressé. Supprimés ; toutes les requêtes passent par la famille `executePrepared*`.

### 🟡 AUDIT-9 — Fuite mémoire lente + rotation cassée (`SyncLogger`)
Le flush drainait max 100 lignes / 500 ms (200 lignes/s) : sous charge soutenue (mass join, poll storms), la queue en mémoire croissait sans borne. Par ailleurs `rotateIfNeeded()` n'était appelé qu'à l'init : le plafond de 10 Mo de `sync.log` n'était jamais appliqué ensuite.
**Fix** : cap porté à 5 000 lignes/flush + rotation vérifiée à chaque flush.

## 2. Constats sans correctif (recommandations)

**Sécurité — connexion MySQL.** `use_ssl=false` par défaut combiné à `allowPublicKeyRetrieval=true` permet à un MITM sur le réseau DB de récupérer le mot de passe (handshake caching_sha2). Acceptable si serveurs et DB sont sur un réseau privé ; sinon activer `use_ssl=true`. Le mot de passe est stocké en clair dans `playersync-common.toml` — protéger les permissions du fichier et utiliser un utilisateur MySQL limité à la base `playersync` (jamais root).

**Sécurité — forge d'items via placeholder.** Le mécanisme de placeholder stocke le NBT original dans le `CustomData` d'un papier. Un joueur en **créatif** peut fabriquer un papier avec un `playersync:original_item_nbt` arbitraire qui sera réinjecté tel quel en DB puis désérialisé en vrai item sur un autre serveur. Sans gravité si le créatif est réservé aux admins ; à garder en tête sinon.

**Config morte restante.** Plusieurs clés sont définies mais jamais lues : `kick_message`, `kick_grace_period_ms`, `skip_saves_when_tps_below`, `log_structured_json`, `log_rotation_size_mb`/`max_files`, et les toggles `sync_inventory`/`sync_ender_chest`/`sync_xp`/`sync_effects`/`sync_health_food` (seuls les toggles mods sont câblés). Soit les implémenter, soit les retirer pour ne pas tromper les admins.

**`server_id` aléatoire.** Le défaut `Random.nextInt(1, MAX)` est généré à la création de la config — deux serveurs clonés depuis le même template partagent le même ID, ce qui casse toute la logique anti-dup. Documenter clairement qu'il faut le fixer manuellement et de façon unique par serveur.

**Hash de snapshot 32 bits.** Le skip « snapshot identique » repose sur un int ; une collision ferait silencieusement sauter une écriture. Probabilité infime mais un passage à un hash 64/128 bits (ou CRC64 du payload sérialisé) éliminerait le risque.

**Poll de join bloquant.** `doPlayerJoin` peut dormir jusqu'à 60 s sur un thread de l'executor (4–16 threads). Une vague de joins simultanés vers des rows contestés peut saturer le pool et pousser `CallerRunsPolicy` à exécuter du SQL sur le thread appelant. Envisager un pool dédié aux joins ou un poll par scheduling plutôt que `Thread.sleep`.

**Build.** `playersync.mixins.json` référence `"refmap": "thirst.refmap.json"` (reliquat d'un autre mod) avec une liste de mixins vide — supprimer le fichier ou corriger le refmap.

## 3. Impact attendu

| Axe | Avant | Après |
|---|---|---|
| Main thread au join | SELECT MySQL + écriture disque bloquants | 0 I/O bloquant (reload seul) |
| Transfert DB au join | toutes colonnes dont blob advancements (Mo) | colonnes utiles uniquement |
| Saves périodiques | 3 mécanismes superposés | 1 (PeriodicSaveService, configurable) |
| Heartbeats SQL | 3 chemins, ~40+ UPDATE/5 min | 1 chemin + piggyback 15 s |
| Dup déco/reco pendant autosave | possible (entité périmée) | bloquée |
| Dup force-claim sur pair vivant | 2 s codées en dur | config honorée |
| DoS NBT-bomb | OOM possible | borné 20 Mo |

## 4. Limites de l'audit

Les corrections n'ont pas pu être compilées dans cet environnement (toolchain NeoForge/Java 21 indisponible) : lancer `./gradlew build` avant déploiement. Les correctifs AUDIT-2/3 (duplication) méritent un test sur serveur de staging : déco/reco rapide pendant l'autosave, et transfert inter-serveurs avec `kick_when_already_online=false`.
